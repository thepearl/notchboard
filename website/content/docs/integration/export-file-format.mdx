A `.notchboard` file is one JSON document holding a whole collection, with every secret-typed value pulled out and sealed under the export password. It is the backup and the no-room sharing path, never the sync channel and no longer the team invitation (that job moved to the [room invite](./room-invite-format.mdx)).

## Top-level shape

* `formatVersion` is the format stamp, currently `1`.
* `workspace` is the catalogue itself, with its groups, field schemas and elements.
* `secrets` is the encrypted envelope, present whenever the source held any secret values.
* `room` is the collection's team room address, present when the collection syncs through one. The room password never travels in a file.

## What is readable in the clear

Element names, usernames, notes, the group schemas, environments, the collection name, and the display name of whoever last used an account are all plaintext. That is a reviewed, accepted trade-off, not an oversight: being able to open a collection file and read it is worth real debuggability.

The per-field lever needs no code change. Mark a field secret in the group designer and its value moves into the encrypted envelope.

## The encrypted envelope

The `secrets` block seals a map of `<elementID>.<fieldKey>` to secret value. It carries three fields:

* `salt` holds 16 random bytes generated per export.
* `rounds` is the PBKDF2-HMAC-SHA256 iteration count, 600,000 by default. Salt and rounds travel with the file so old exports stay decryptable when the default cost rises later.
* `sealed` is the AES-GCM combined representation (nonce, ciphertext and authentication tag).

The key chain is the export password through PBKDF2, then HKDF with the info string `nb-export`, then AES-GCM. The HKDF step keeps the export key unrelated to the room key even when someone reuses the same password for both.

Because AES-GCM authenticates, a wrong password fails the tag check and is reported as exactly that. It can never decrypt into plausible garbage, and a tampered file fails closed.

## What never travels

* Marks of who is using what are stripped on export. A mark frozen into a file arrives stale by construction, so no `claimedBy` key appears anywhere in a `.notchboard` file.
* Secret values never appear in the clear. Their in-band slots inside the workspace JSON are blanked before the file is written.
* The room password never appears, even when the `room` block does. It is shared out of band.

## Import rules

* A file with any other `formatVersion` is refused, not migrated. Pre-release there is exactly one format, checked exactly.
* In-band secret values in a hand-edited file are ignored. Whatever the file contains, those slots are force-blanked on import, and real values only enter through the authenticated envelope, which cannot be forged without the password.
* Envelope values only land in fields the schema actually types as secret, so an envelope cannot smuggle values into non-secret fields either.
* Any in-use marks a hand-edited file carries are stripped the same way.
* Importing adds a new collection. It never overwrites an existing one.

## Strength

A file is exactly as strong as its export password. That is why the export prompt offers a passphrase generator.

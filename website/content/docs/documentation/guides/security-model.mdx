Read this before putting anything sensitive into a room or an export file.

<Callout type="warn">
None of this has had an external security review. Notchboard is a pre-release project, and the design reasoning is written up in the repository for anyone who wants to check the working.
</Callout>

## The one-line summary

In a room, everything in the payload is encrypted. In a file, only secret-typed values are. Those are opposite splits and they are worth keeping straight.

## Room encryption

Every room payload is sealed with AES-GCM under a key derived from the room password, through PBKDF2 at 600,000 rounds with a salt derived from the broker host and room name, then HKDF over the result for domain separation from the export password.

The broker relays bytes it cannot read. Send the wrong room password and messages fail to open cleanly rather than being applied as garbage.

### One key for the whole room

The room password is the entire security boundary. There are no per-member keys and no roles.

Anyone who has held that password can read every value in that collection, secrets included, and keeps that ability after they leave. Rotating a room password in place is refused, because everything the broker retains is ciphertext under the old key, so rotating would lock the room's own members out.

Removing someone means creating a new room and reinviting everyone else. There is no server, so there is nobody to revoke them at.

### Topic names are not encrypted

A broker operator sees the room name, your group names, the internal ids of every element and member, exactly how many groups, elements, live in-use marks and members exist, which element was taken and at what second, and who is online.

On a public broker, so does everyone else who cares to subscribe.

Pick a room name that gives nothing away, and prefer a broker you control.

<Callout type="error">
A public test broker is the fastest way to see a room running, and the wrong place for anything you care about. Use one for a trial with throwaway data only.
</Callout>

### The offline grinding problem

The salt is derived rather than random, and retained messages sit on the broker indefinitely, so anyone able to subscribe can collect ciphertext and grind the room password offline at their leisure.

The 600,000 rounds are what make that expensive. A weak room password is the one thing that undoes all of it, which is why the dialog has a generator.

## File encryption

An export file protects secret-typed values only. Element names, usernames, notes, schemas and environments are readable plaintext in the file. So is the room block, if the collection has one: broker address, port, account username and room name, with only the broker account password as ciphertext inside it.

In-use marks are stripped on export, but names are not. The collection carries a member list mapping member ids to display names, and every element keeps the member id of whoever last edited it. Both travel in the clear.

That plaintext is a deliberate trade-off, because being able to open a collection file and read it is worth the debuggability. The per-field lever is the field type.

## Where secrets sit at rest

| Surface      | What is there                                                        |
| ------------ | -------------------------------------------------------------------- |
| `state.json` | Keychain placeholders, never real secret values                      |
| Export file  | Secret values inside an authenticated AES-GCM envelope               |
| Snapshot     | The whole state sealed as one box, under a device-local key          |
| Keychain     | The real secret values, room passwords, and the snapshot sealing key |

There is one deliberate exception. A failed Keychain write is never treated as stored, so the value stays in `state.json` rather than being replaced by a placeholder pointing at nothing. Persisting a placeholder that points at nothing would turn a transient locked keychain into permanent loss of the secret.

## The accepted exposures

There is one place a password leaves the Keychain in the clear.

`simctl` and `adb` both take the deeplink URL as a command-line argument, so while that short-lived process runs, a password in the query is readable by other processes running as you. There is no argv-free way to hand either tool a URL.

Android adds one exposure of its own: emulators on API 32 and older log the intent's URL verbatim to logcat, credentials included. API 33 and later redact it.

These are shared test credentials on a local developer tool, so the exposures are documented rather than hidden, and everything under the app's own control is redacted.

The update check is the one network request that is not a room. Once a day, starting at first launch, and whenever you ask, Notchboard fetches a small file from GitHub's releases page. GitHub sees your IP address, a user agent naming the app and its version (`notchboard/1.2 Sparkle/2.9.6`) and the time, and nothing else.

An update installs only if its signature checks out against the release key shipped inside the app and its Apple signature is valid. Both keys live as secrets in the release repository, so anyone who can push a tag there can sign a release with both. The two signatures protect the download in transit and on the CDN, not against a compromised maintainer account. A Homebrew install additionally trusts the tap repository, whose cask names the URL and checksum brew fetches. Settings turns the automatic check off.

## What Notchboard is not

* Not a password manager. Your personal secrets belong somewhere with a different threat model.
* Not a production secrets store. The production-mix warning is the whole mechanism, and there is no policy engine behind it.

## Practical advice

* Generate the room password and the file password. Both dialogs offer it.
* Prefer a broker you control over a public one.
* Pick a room name that reveals nothing about the client or the product.
* Mark anything that should not sit in a plaintext file as `secret`.
* Never put real production credentials in a collection that syncs to a room.
